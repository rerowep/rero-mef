Every BNF number bib.rero.ch holds, and whether it links

The linking rule joins an IdRef concept to a GND concept when both name the same normalised BNF number and nothing about that number is ambiguous. This page takes the — BNF numbers carried by a topic concept bib.rero.ch actually uses — behind them — subject references — and says for each one whether it links today, and if not, which side blocks it.

— link in production. The rest fail for one of three distinct reasons, and only one of them can be fixed here.

By catalogue weight, not by row count

How many subject references in bib.rero.ch sit behind each state. A blocked number that carries hundreds of documents costs more than a hundred that carry none.

The four outcomes

linked One GND names this number, unambiguously, and the cluster exists in production.
idref · several gnd The IdRef side is blocked. Two or more GND concepts claim the same number, so the IdRef concept holding it faces a choice the rule refuses to make. Fixing it means deciding which GND concept the number belongs to.
gnd · several numbers The GND side is blocked. Exactly one GND concept claims the number, but its winning match block names two or more different BNF numbers — which states no usable identifier at all. Fixing it means choosing in GND, not guessing here.
unlinked No GND concept claims this number in either exactMatch or closeMatch. Nothing is blocked; there is simply nothing on the other side to link to.
should link, doesn't Nothing is blocked, and there is still no link. Exactly one GND concept claims the number, it names no other number, neither side is already taken — and mef.rero.ch holds the two in separate single-source clusters anyway. Spot-checking the 41 of the 2026-09-08 snapshot ruled out a stale index, a competing partner, the match level, and record age: 40 of them are indistinguishable from rows that do link. The cause is not visible from the public APIs, so this is the one state that has to be settled from inside the linking job.
